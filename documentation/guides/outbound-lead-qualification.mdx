title: "Outbound lead qualification"
description: "An outbound voice agent, a CRM write-back, post-call analysis and a scheduled campaign, end to end."
---

You are going to build a campaign that calls a list of leads, opens by saying who is calling and why, asks four qualifying questions, writes the answer back to your CRM, and leaves behind a call record you can filter into a shortlist. When it is finished you will have one published agent, one published tool, one outbound-capable number, and a batch that dials on a schedule you set, retries the phones nobody answered, and stops itself if something is broken.

<Warning>
Two things decide whether this campaign is a good idea, and both are easier to accept now than from an invoice.

- **Voicemail is still a billed call.** The agent below turns on [voicemail detection](/agents/voicemail), so a call that reaches a machine leaves a short message, hangs up, ends as `voicemail` and is retried like a missed call. It connected, so it is billed at the full platform fee — a list with many machines costs money even when it reaches nobody.
- **Every call in a batch runs your agent's current published version.** The batch re-reads it before each dial, so republishing at 14:00 changes every call placed from 14:00 onwards, including the rest of a campaign that has been running since morning. If you need a campaign held steady across an edit, pin it — see [batch calling](/telephony/batch-calling).
</Warning>

<Step title="Personalize each call with the recipient's own userdata">

Each row of a batch carries `to` plus a flat map of strings that becomes that call's session state, and `{{userdata.field}}` in the prompt and the greeting is substituted from it when the agent starts. One published agent, a different opening line per lead.

```json
{ "to": "+919876543210", "userdata": { "first_name": "Priya", "company": "Asha Textiles", "crm_id": "lead_88213" } }
```

**A field that is not in userdata resolves to nothing**, so put the token where an empty value still leaves a sentence. `"Hi {{userdata.first_name}} — this is Maya from Northwind Tools"` still reads if the name is missing; `"Hi, am I speaking to {{userdata.first_name}}?"` does not. Values are strings on purpose — a spreadsheet cell reading `007` is a reference number, not the integer seven. See [userdata](/agents/userdata).

### Branching the opening on the call direction

If the same agent also answers inbound calls on that number, the greeting has to differ: outbound says who is calling and why, inbound does not. A greeting is one verbatim line and has no conditionals, so put the branch in an `on_enter` hook, which finishes **before** the greeting and whose writes to userdata the greeting then reads.

Create this tool, publish it, and set the agent's `greeting` to `"{{userdata.opening}}"`:

```json
{
  "name": "choose_opening",
  "description": "Lifecycle hook: pick the opening line for this call's direction.",
  "json_schema": {},
  "operations": [
    {
      "kind": "if",
      "config": { "left": "{{system_vars.direction}}", "op": "eq", "right": "outbound" },
      "then": [
        {
          "kind": "set_variable",
          "config": {
            "key": "opening",
            "value": "Hi {{userdata.first_name}} — this is Maya from Northwind Tools, calling about the capacity planning guide you downloaded. Is now a bad moment?",
            "store": "userdata"
          }
        }
      ],
      "else": [
        {
          "kind": "set_variable",
          "config": {
            "key": "opening",
            "value": "Northwind Tools, this is Maya. How can I help?",
            "store": "userdata"
          }
        }
      ]
    }
  ]
}
```

Attach it as `"on_enter": { "tool_id": "7a2e5b91-0c34-4d6f-8a12-b93f5c7e2d61" }`.

<Warning>
Keep this hook to `set_variable` operations and nothing else. If the hook fails, the call carries on but `{{userdata.opening}}` resolves to nothing — and **an empty greeting on first entry means the agent says nothing at all** and waits for the other person to speak. On an outbound call that is dead air into a stranger's ear. A hook that only writes two strings has nothing that can fail; a hook that calls an HTTP endpoint does.
</Warning>

`{{system_vars.direction}}` is `inbound` or `outbound` and is empty on web calls and text conversations. See [variables](/agents/variables).

</Step>

<Step title="Turn on post-call analysis">

The tool writes what the agent was *told*. Analysis writes what a reader *infers* from the finished transcript, which is what makes a campaign readable without listening to four hundred calls. Add it to the agent's config:

```json
{
  "analysis": {
    "enabled": true,
    "summary": true,
    "outcome": {
      "prompt": "A successful call is one where a real person answered, agreed to talk, and gave an answer on both budget and timing — even a negative one. A call that reached voicemail, was cut off in the first fifteen seconds, or ended with the person asking to be left alone is a failure."
    },
    "fields": [
      { "name": "fit", "type": "string", "description": "How well this lead matches a mid-market distributor with a warehouse, judged from what they said about their operation. One of: strong, possible, poor, unclear. Use unclear if the call was too short to tell." },
      { "name": "budget", "type": "string", "description": "What they said about money, in one short phrase, e.g. 'about 20 lakh approved for this year' or 'no budget until April'. Use 'not discussed' if it never came up." },
      { "name": "timeline", "type": "string", "description": "When they said they would want something in place, in one short phrase. Use 'not discussed' if it never came up." },
      { "name": "next_step", "type": "string", "description": "The single next action a salesperson should take, written as an instruction, e.g. 'send the integration one-pager to the ops head'. Use 'none' if the person asked not to be contacted again." }
    ]
  }
}
```

<Note>
**Analysis fields and userdata answer different questions, and one must not be used for the other.** `userdata` is what the agent *knew* — seeded from the recipient row, written by a tool, confirmed on the call. Analysis fields are what a model *inferred* afterwards by reading the transcript. Analysis results are never merged into userdata, deliberately: a guess must not overwrite a tool-confirmed value.

So `budget_band` on the CRM write is an argument the model filled in while the person was on the line, and it is what you act on. `budget` in the analysis fields is a sentence a reader can scan. If a value has to be right, make it a tool argument. If it only has to be readable, make it an analysis field.
</Note>

Analysis runs on the agent's own LLM, so it needs no second provider key. It adds roughly 5% to the cost of a call and runs during call finalize, so its tokens land in the same bill. A call is skipped rather than analysed when it ended on a failure reason, when fewer than two caller turns happened, or when the spec produces nothing. See [call analysis](/observability/call-analysis).

In the dashboard this is **Telephony → Outbound Calling → New batch**, which takes the same fields and a pasted or uploaded list.

The four numbers that decide how it behaves:

| Field | Range | Default | What to pick |
| --- | --- | --- | --- |
| `max_concurrency` | 1–10 | **1** | 2 or 3 while you are still reading transcripts; higher once the agent has earned it. The default is 1 because an unstated intention about something that spends money should be read conservatively. |
| `max_attempts` | 1–5 | **1** | 2 or 3 for a cold list, where most first dials go unanswered. The default is 1 for the same reason: nobody should discover they called a stranger three times. |
| `retry_after_minutes` | 5–1440 | 30 | 90 or more. Ten minutes later is the same hour of the same day and usually the same voicemail. |
| `calling_window` | — | any hour, any day | Set it. Without one a list uploaded at 23:00 starts dialling at 23:00. `days` are ISO weekdays with 1 = Monday. |

`timezone` is the batch's own clock, and it interprets `calling_window` — so the window is the *recipients'* working day, not the working day of whoever pressed the button.

## Test it

Before the list runs, prove each piece separately on the single call you placed.

1. **The transcript.** `GET /v1/calls/{session_id}` returns the transcript with every tool call and its output, plus per-stage latency. Check the greeting was substituted, that the agent gave the way out inside the first three sentences, and that `record_qualification` was called once rather than twice.
2. **The CRM row.** Look in your CRM, not at the tool's response. The `http` operation is `silent`, so a 200 with the wrong body looks identical to a correct write from the agent's side.
3. **The analysis.** Read `analysis.status`, `analysis.outcome` and `analysis.fields` on the same call. If a field came back vague, that is the field's `description` failing, not the model — rewrite it and use `POST /v1/calls/{session_id}/analysis/preview` to try new wording against the same transcript. Preview writes nothing and still costs a real LLM call.
4. **A two-row batch to phones you own.** Create the campaign with two of your own numbers and `max_concurrency: 1` before you create it with four hundred. Everything about scheduling, retries and counters is the same shape at two rows as at four thousand.

## Running it

`next_dial_at` is the field that tells "waiting for Monday" apart from "stuck". It is null while the batch is actually dialling, while a person has it paused, and once it is over — all three of which `status` already tells you.

- **Pausing** stops claiming new recipients; calls already ringing or connected run to their end. **Resuming** carries on, and a batch whose `start_at` is still in the future goes back to `scheduled` rather than `running` — pausing and resuming is never a way to start early.
- **Adding rows to a running batch** works: `POST /v1/calls/batches/{batch_id}/recipients` appends, and numbers the batch already holds are **silently skipped and reported** rather than rejected. Re-uploading the same CRM export never calls anyone twice.
- **The circuit breaker** stops a batch after **ten consecutive** setup-style failures — a carrier fault, an unpublished agent, an expired credential. The count is rolling and any success resets it, and busy signals and unanswered phones never count towards it: a run of those is a phone list, not a fault.
- **Running out of credit pauses the campaign rather than failing it.** No attempt is spent on anybody, `failure_reason` says the workspace is out of credits, and it resumes on its own once you top up. There is no button to press.
- **Cancel is final.** A finished batch can be deleted, which removes its recipient list; the calls it made stay.

The full behaviour of every one of these — statuses, the retry table by close reason, policy edits — is in [batch calling](/telephony/batch-calling).

## What to watch

| Where | What it answers |
| --- | --- |
| `GET /v1/calls/batches/{batch_id}` | `counts` (total, pending, dialing, completed, failed, canceled), `status`, `next_dial_at`, `failure_reason`. |
| `GET /v1/calls/batches/{batch_id}/recipients?status=failed` | Per person: `attempts`, `last_close_reason` and a plain sentence in `last_close_reason_label`. |
| `GET /v1/calls?batch_id=…` | The calls themselves, with `summary` and `outcome` on each row. Add `&outcome=success` for the ones that got an answer. |
| `GET /v1/calls/{session_id}` | The only place the custom analysis `fields` appear — the list gives you `summary` and `outcome`, not the four fields. |
| The `session.completed` webhook | Carries `analysis.summary`, `analysis.outcome` and `analysis.fields` for every call as it lands, plus `batch_id`. If you want a shortlist in your own system rather than a script that fetches each call, subscribe to this. See [webhooks](/observability/webhooks). |

Turning the campaign into a qualified list, then, is two filters and a fetch: list the batch's calls with `outcome=success`, fetch each one, and keep the rows whose `fit` is `strong` or `possible`. The `next_step` field is what a salesperson reads first.

## Where it falls short

- **Voicemail detection is the model's judgement.** It hears the machine's greeting and decides, so an unusual greeting can slip through as a conversation with nobody, and each retry that reaches the same mailbox leaves the message again. `counts.voicemail` on the batch says how many recipients' latest call was a machine.
- **One batch is one agent, one number, one clock.** There are no per-recipient overrides of anything but `userdata`. Half a list needing a different agent, a different caller ID or a different language is a second batch.
- **The batch runs as the person who created it.** Every dialling pass re-authorizes as that user. If they leave the workspace or drop below the EDITOR role, their campaign records a configuration failure on the next pass, and ten of those trip the breaker. Hand running campaigns over before somebody leaves.
- **Calling law is yours to know.** Consent, do-not-call registers, permitted calling hours, disclosure requirements and recording law differ by country and by state, and Talqing enforces none of them. `calling_window` is a scheduling feature, not a compliance one — it does not know a public holiday from a Tuesday.
- **Analysis is a reading, not a record.** It is one LLM call over the transcript, with a 30-second timeout, three-valued on purpose so that a wrong number comes back `unknown` rather than being forced into a verdict. Back a business decision with what a tool confirmed, not with what a summary suggested.
