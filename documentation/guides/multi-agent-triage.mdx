title: "Multi-agent triage"
description: "A front desk that greets every caller and routes to billing, technical support and sales, each with its own prompt and tools."
---

You will build four agents on one phone number: a front desk that greets the caller, works out what they need in a question or two and hands them on, plus three specialists that each hold one job, one prompt and one set of tools. You will also add one route the model does not decide — a lookup that sends a caller with an open ticket straight to technical support.

The example is Northwind Tools. Every hop here is a [handoff](/teams/handoffs) — agent to agent, on the same call. Handing the caller to a **person** is a [transfer](/tools/transfer), and the two are never interchangeable.

## Should you split at all?

Splitting is not free. Every hop pauses the call while the target is built, and the target then pays for whatever context crossed on **every turn it takes**, on your own provider key. One agent has neither cost.

| Split when | Do not split when |
| --- | --- |
| One prompt is holding three policies and picking between them badly | Two agents' prompts would differ by a paragraph. That is one agent with a better prompt |
| The desks want different models, voices or languages | You only want the tool list shorter. Attach fewer tools |
| A tool must be reachable from one desk and not another — the refund tool on billing, and nowhere the front desk can call it | The routing is a lookup rather than a judgement. That is one agent and a [conditional route](/teams/conditional-handoffs), which is step 4 below |

Three desks is about the point where it pays. Below that, the descriptions overlap and the caller gets passed around.

## What you need

| | Why |
| --- | --- |
| Provider keys for the models each agent names | Every agent on the call runs on your own keys. See [provider keys](/get-started/provider-keys) |
| An HTTPS endpoint that looks an account up by phone number, and a bearer token for it | For the conditional route in step 4 |
| An HTTPS endpoint that reads an invoice, and a bearer token for it | For billing's tool |
| A [workspace secret](/platform/secrets) named `NORTHWIND_API_KEY` holding that token | Both tools read it as `{{secrets.NORTHWIND_API_KEY}}`, and publish fails on a secret that does not exist |
| A phone number for an account executive, in full international format | Sales transfers to a person |
| A carrier number and a Talqing token | See [phone numbers](/telephony/phone-numbers) |

<Steps>

<Step title="Build and publish the three specialists">

**Publish these first.** A handoff edge whose target has no published version is refused when you publish the front desk, so the graph is built leaves-first.

Each specialist gets a short prompt covering one desk, and — this is the part people leave out — a line telling it **not** to re-litigate which desk the caller wants. It has already been chosen. A specialist that re-routes sends the caller round the loop.

### Billing

```text
You are the billing desk at Northwind Tools. The caller has already been
passed to you by the front desk, so do not introduce the company again and do
not ask what they are calling about if you can already see it.

You handle invoices, refunds, payment questions, card details and anything
about what the caller has been charged.

RULES
- Ask for the invoice number before you look anything up, and read it back.
- Say an amount only if it came back from look_up_invoice. Never estimate one.
- Never read a card number back, and never ask for one.
- If the caller asks about something that is not billing, hand them back to
  the front desk rather than trying to help.

TOOLS
- look_up_invoice: say "let me pull that invoice up, one moment" before you
  call it, then answer in your own words.

SPEAKING
- Two or three sentences per turn. Let the caller cut in.
- No markdown, no lists, no emoji and no JSON in what you say.
- Say amounts as words: "two thousand four hundred rupees", never "Rs 2400".
- Say dates as "Thursday the ninth of April", never "09/04".
- Read an invoice number back one character at a time, in groups.
```

Its invoice lookup is defined **inline**. On an agent that is a shorthand: the write creates the tool, publishes it at v1, and stores its id in place, so an agent and its tools arrive in one request. It is not a second kind of tool — read the config back and you will find a `tool_id`.

Save the prompt above as `billing-prompt.txt`, then:

### Technical support

Same shape, with no tool: the troubleshooting facts it needs are in its prompt.

```text
You are the technical support desk at Northwind Tools. The caller has already
been passed to you by the front desk, so do not introduce the company again.

You handle tools that will not start, will not charge, throw an error code, or
were set up wrong.

TROUBLESHOOTING
- Will not start: check the battery is pushed fully home until it clicks, then
  try a second battery if they have one.
- Will not charge: a flashing red light on the charger means the battery is
  too hot or too cold. Leave it at room temperature for an hour and try again.
- Error E1 is overheating: let the tool cool for fifteen minutes. E2 is a
  jammed motor: remove the battery and clear the chuck or blade.
- Anything else, or a fault that survives these steps, is a warranty repair.

Answer only from the lines above. If they do not cover it, say so plainly and
offer to raise it with an engineer. Never guess at a fix that involves opening
a tool or a battery.

RULES
- Ask for the model number on the tool before you diagnose anything. It is on
  the plate near the cable.
- One instruction at a time. Wait for the caller to do it before you give the
  next one.
- If the caller starts asking about a charge or a refund, hand them to
  billing.

SPEAKING
- Two or three sentences per turn. Let the caller cut in.
- No markdown, no lists, no emoji and no JSON in what you say.
- Read a model number back one character at a time: "N W - D - two one zero".
- Say error codes character by character, never as a word.
```

### Sales

Sales does not close on the call — it qualifies and puts the caller through to a person, so its one tool is an argument-free transfer with the escalation policy in the description.

```text
You are the sales desk at Northwind Tools. The caller has been passed to you
by the front desk and may not have said much yet, so start by finding out what
they need.

GOAL
Find out three things and nothing more: what they want to buy or fit out,
roughly how many, and when they need it. Then put them through to an account
executive.

RULES
- One question at a time. Wait for the answer.
- Do not quote a price, a discount or a lead time. Say the account executive
  will go through those.
- Do not take card details, ever.
- If it turns out they are an existing customer with a problem rather than a
  purchase, say so and hand them back to the front desk.

TOOLS
- transfer_to_account_executive: once you have all three answers, or as soon
  as the caller asks for a person.

SPEAKING
- Warm and quick. Under two sentences per turn.
- No markdown, no lists, no emoji and no JSON in what you say.
- Say quantities and dates as words.
```

That transfer is `warm`: the caller waits on hold music while the agent briefs the account executive on a separate line, and only then puts the two together. It costs a second AI conversation on your own keys, and the person answering can decline — in which case the caller comes back to the sales agent. The `say` in front of it is worded for `warm`; before a `cold` transfer the same line would be a lie. See [transfer](/tools/transfer).

Publish all three before going on.

<Step title="Build the front desk">

The front desk carries one `handoffs` entry per desk. Each entry becomes **one tool the model can call**, named `handoff_to_<name>`, and the model routes on that entry's `description` and nothing else.

Write each description as **what belongs there**, never as an instruction to the model:

| Write this | Not this |
| --- | --- |
| `invoices, refunds, payment questions, card details and anything about what the caller has been charged` | `Use this when the caller has a billing problem` |
| `a tool that will not start, will not charge, shows an error code, or was set up wrong` | `Hand off to technical support when appropriate` |
| `buying anything new - a quote, a bulk order, fitting out a site, or a product they do not own yet` | `Call this for sales enquiries` |

Descriptions that do not overlap are most of the work. If billing says "payments" and sales says "orders", a caller asking about a payment for an order they have not placed is a coin flip. Put the ambiguous words in exactly one description, deliberately.

The front desk's own prompt is short, and most of it is about what it does **not** answer. An agent with three handoff tools and a prompt inviting it to be helpful will answer the billing question badly instead of routing it.

```text
You are the front desk at Northwind Tools, which sells power tools. Your only
job is to find out which desk the caller needs and pass them to it.

First, call route_by_open_ticket. If it hands the call on, you are done. If it
does not, carry on below.

Find out what the caller needs in one question, two at most, and then hand
them over. Do not answer a billing, technical or sales question yourself, even
when you think you know the answer - the desks have the account and the tools,
and you have neither.

If the caller says two things at once, ask which they want dealt with first
and route on that.

SPEAKING
- One or two sentences per turn. Let the caller cut in.
- No markdown, no lists, no emoji and no JSON in what you say.
- Do not say the word transfer, and do not name the desk you are sending them
  to twice.
```

Save it as `front-desk-prompt.txt`, then create it.

</Note>

### Why each edge carries what it does

`context` decides what the target starts from, and it is the field that costs the most money on a team. Justify every edge rather than taking the default three times.

| Edge | Policy | Why | What the target then pays on every turn |
| --- | --- | --- | --- |
| Front desk → Billing | `transcript` | The handover happens two or three turns in, so "everything so far" **is** two or three turns. Asking for a summary here would buy a pause before the handoff and a shorter version of something already short | Two or three turns |
| Front desk → Technical support | `transcript` | Same, and the desk needs the caller's exact words about what the tool is doing — a summary loses "it clicks twice and stops" | Two or three turns |
| Front desk → Sales | `none` with `recent_turns: 2` | Sales runs its own qualification from the top and does not want the triage framing in its context. The two-turn tail is what tells it what the caller actually asked for | Two turns, and nothing else |
| Technical support → Billing | `summary` with `recent_turns: 3` | This hop happens twenty turns in, after a diagnostic. `transcript` would make billing re-read the whole thing on every reply it gives | Roughly a paragraph, plus three turns |
| Billing → Front desk | `none` with `recent_turns: 2` | The front desk's job is to route, and routing needs the last thing the caller said, not the billing detour. Under `transcript` it would route on a question that has already been answered | Two turns |

Two rules the API enforces rather than ignores: `recent_turns` is **refused** under `transcript`, which already carries every turn, and `summary_prompt` is refused outside `summary`. Under `summary`, the source agent writes the summary itself as an argument on the `handoff_to_*` tool — there is no second model call, but the caller waits through 60 to 100 tokens before the handover happens. Full rules in [context policies](/teams/context-policies).

<Warning>
**`summary` is not a privacy boundary.** It narrows what the target model is shown and guarantees nothing: the tail always crosses, `userdata` crosses regardless, the full transcript is still recorded, and a later `transcript` hop shows that agent the whole call including the part `summary` scoped away. If a fact must not reach the next agent, do not let the first agent hold it.
</Warning>

### The handover message

`message` is queued **before** the target is built, which is the whole point of it: building the target loads its definition and compiles its prompt, tools and voice, and the caller should hear "connecting you to billing" during that pause rather than after it. It always finishes playing before the target's own greeting.

On a cascade agent it is spoken verbatim. Leave it out and the handover is silent, which is fine when the target has a greeting of its own — but then the caller hears two seconds of nothing followed by a new voice, so say something.

</Step>

<Step title="Route on a lookup instead of on the model">

Whether a caller has an open ticket is a fact about their account, not a judgement about what they said. Facts belong in a tool tree. The [`handoff` operation](/teams/conditional-handoffs) is the same move as an edge on the agent, except the **tree** decides.

This tool assumes your endpoint answers `200` with all three keys on every response — `open_ticket_id` and `open_ticket_summary` as empty strings when there is nothing open. That matters: `publish_fields` fails the operation when a path is missing **or null**, so an endpoint that omits a key on the quiet path breaks the tool on exactly the calls it is meant to pass through.

```json
{
  "name": "route_by_open_ticket",
  "description": "Check whether the caller already has an open support ticket, and send them straight to technical support if they do. Call it once, as the very first thing you do on every call, before you ask the caller anything.",
  "json_schema": {},
  "operations": [
    {
      "kind": "http",
      "config": {
        "method": "GET",
        "url": "https://api.northwind.example/v1/accounts/lookup",
        "query": { "phone": "{{system_vars.human_phone_number}}" },
        "headers": { "Authorization": "Bearer {{secrets.NORTHWIND_API_KEY}}" },
        "timeout": 5
      },
      "on_error": "continue",
      "silent": true,
      "publish_fields": [
        { "path": "customer_name", "key": "name", "store": "userdata" },
        { "path": "open_ticket_id", "key": "ticket_id", "store": "tooldata" },
        { "path": "open_ticket_summary", "key": "ticket_summary", "store": "tooldata" }
      ]
    },
    {
      "kind": "if",
      "config": { "left": "{{tooldata.ticket_id}}", "op": "neq", "right": "" },
      "then": [
        {
          "kind": "handoff",
          "config": {
            "target_agent_id": "7d2e5a04-91c3-4f68-b0aa-2c53e7d19f80",
            "context": "summary",
            "summary": "The caller rang the main line. There is already an open ticket on their account: {{tooldata.ticket_summary}}. They have not been asked anything yet.",
            "recent_turns": 1,
            "message": "I can see an open ticket on your account - let me take you straight to technical support."
          }
        }
      ],
      "else": [
        {
          "kind": "generate_reply",
          "config": {
            "instructions": "There is no open ticket on this caller's account. Ask, in one short question, what they are calling about."
          }
        }
      ]
    }
  ]
}
```

Four things that tree is doing on purpose:

- **`on_error: "continue"` on the lookup** is what stops a flaky endpoint taking the front desk down with it. A failed operation publishes nothing, so `{{tooldata.ticket_id}}` resolves to empty, the `if` takes its `else`, and the caller gets an ordinary greeting instead of an apology.
- **`context: "summary"` here takes a value, not a request.** The tree runs *after* the model's tool call, so there is no argument being written at that moment to take a summary from. Point it at something real — a template over `tooldata`, as above, or fixed prose. A `summary` under any other context is an error.
- **The `if` is terminal and branches do not rejoin.** Nothing may follow it in the same chain, so anything both paths need goes before it or into both branches.
- **The `else` speaks.** No operation in this tree can return a response, so the tool is silent by derivation — without the `generate_reply` the agent would fall quiet after the lookup. Adding a `generate_reply` that states what to say is the right way to break that silence; there is no flag to untick.

`POST` it to `/v1/tools`, `validate` it — `target_agent_id` must already be published, which is why the specialists came first — and `publish` it before attaching it to the front desk. The examples in step 2 call the created tool `route`. Then publish the front desk.

</Step>

<Step title="Keep the team sounding like one company, then go live">

Every agent above shares `language`, `stt`, `tts` and its voice. That is not laziness — it is the difference between a caller being passed to a colleague and a caller wondering whether the line dropped.

| Constraint | Enforced? | What happens |
| --- | --- | --- |
| Same channel, and same pipeline — both cascade, or both realtime | **Error at publish** | There is no media path from a `voice` agent to a `text` one, and swapping a speech-to-speech socket for an STT/LLM/TTS stack mid-call would mean rebuilding the media graph |
| Out of an [expressive](/agents/expressive-delivery) agent, every target uses the **same** provider, model and `expressive: true` | **Error at publish** | The target inherits a transcript full of delivery tags and starts writing its own; a voice that cannot speak them reads them out. Handing off *into* an expressive agent is fine, so the rule is transitive — one expressive agent puts its whole downstream graph on one voice |
| Same voice and language across desks | **Nothing checks this** | A team can hand a caller from one voice to a completely different one mid-call. Either give every member the same `tts` block, or have each target's greeting say who it is |
| Recording on across the team | **Warning at publish** | Recording cannot *start* part-way through a call, so if the agent that answers has it off, nothing is recorded even where a target has it on. Switching off mid-call always works |

Validate every agent, then publish, then put the front desk on the number. **The agent assigned to a number is the one that answers** — the specialists are reached only through handoffs and are never assigned to anything.

## What to watch in the first week

**Which agent said each line.** Every transcript item stamps its own `agent_id` and `agent_version` as it was produced. The session names only the agent that **answered** and never moves, so on a call with a handoff these stamps are the only way to tell who said what. `GET /v1/conversations/{conversation_id}/sessions` is deliberately the same: it names the agent that picked up, not the one that did the work. See [conversations](/observability/conversations).

**Where the handovers are, and what crossed.** The transcript carries an `agent_handoff` item at each boundary. Beside it, `events` carries an `agent.handoff` entry with the policy, the resolved `recent_turns`, `tail_items` — how many messages the tail actually came to, usually more than `recent_turns` because a turn can hold several — the summary itself, `summary_fallback`, and `via`, which is `handoffs` for an edge on the agent and `operation` for the conditional route above.

**Telling a mis-route from a bad prompt.** These look identical in a summary and are completely different problems, and the transcript separates them in one glance:

| What you see | What it is | The fix |
| --- | --- | --- |
| The `handoff_to_*` call happens on a turn where the caller clearly said which desk they wanted, and it goes to the wrong one | A **routing** problem. Two descriptions overlap on the words the caller used | Move the ambiguous words into exactly one `description`. Nothing else changes |
| The right desk was reached and then answered badly, or asked for something the caller already said | A **prompt or context** problem on the specialist | Read what actually crossed on that edge. If the target asked the caller to repeat something, the policy carried too little; if it re-read a resolved question, too much |
| The caller bounces between two desks | Both, and it will hit the 25-hop cap | Two descriptions claim the same ground, or a specialist's prompt lets it re-litigate the routing. Add "do not decide which desk the caller needs" to the specialist |
| A handover that takes noticeably longer than the others | The edge is on `summary`, and the source is writing 60–100 tokens before the tool returns | Only pay that where the call is long enough to be worth summarizing |

**The `reroutes` field.** Any call above 1 is worth opening. Read those before you read the failures — a caller who reached the right desk on the third try counts as a success and is still a bad call.

## Where this falls short

**Routing quality is a description-writing problem, and it is iterative.** There is no model, threshold or confidence score to turn up. The model reads three descriptions and picks one, so the only lever is the wording — and the loop is: read the transcripts where it chose wrong, find the caller's exact phrase, and put that phrase in one description. Change one description at a time; changing three at once means you cannot tell which fixed it. A description that has grown into three sentences of instructions is a sign the split itself is wrong.

**Every hop costs latency, and it stacks.** At the boundary the platform loads the target's published definition, its pinned tools and its hooks, and builds its models — that pause is what the `message` exists to cover. Under `summary` there is a second pause first, while the source writes the summary. Then the target's `on_enter` hook runs to completion before it says a word. Two hops on a short call are unnoticeable; three hops with `summary` on each is a call that feels slow, and the caller has no idea why. Watch `snapshot.response_latency.p95_ms` on multi-agent calls specifically.

**There is no way to test a routing change before it faces real callers.** No staging environment, no simulated caller, no test suite that replays past calls against a new set of descriptions — none of that exists here. The closest thing is real and worth using: place a call against the **draft** rather than the published version by passing `agent_version: "draft"` on a call token or an outbound dial, so you can hear an edit without publishing it over what live callers are getting. Beyond that, change one description, publish, and read the next twenty calls.

Two smaller limits. `summary` is not a privacy boundary — see the warning above — so a team is not a way to keep one desk from seeing another's conversation. On **text** a handoff lasts for the rest of the chat: whichever agent was last handed the conversation answers every later message, until the chat ends. See [chats](/channels/text-conversations).
