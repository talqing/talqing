---
title: "Inbound support line"
description: "A voice agent that answers your support number: your policies in its prompt, a tool for the caller's order, and a person when it should."
---

You will build a voice agent that answers a real phone number, answers policy questions from the policies you give it, looks a caller's order up through your API, and hands the call to a person when it should. By the end the number is live, every call is transcribed and summarized, and you can list the calls that went wrong.

The example company is Northwind Tools, an online shop selling power tools. Substitute your own domain, endpoint and numbers as you go — everything else pastes as written.

## What you need

| | Why |
| --- | --- |
| A Talqing workspace with credit | Voice carries a per-minute platform fee. See [pricing and credits](/get-started/pricing-and-credits) |
| Provider keys for OpenAI and Deepgram | Talqing is strictly bring-your-own-key and an agent will not publish without a key for every provider it names. See [provider keys](/get-started/provider-keys) |
| A public HTTPS endpoint that returns one order as JSON, and a bearer token for it | Tools cannot reach a private network. See [the HTTP operation](/tools/http) |
| Your returns, delivery and warranty policies, in a few short paragraphs | They go into the prompt, so the agent answers from them and nothing else |
| A carrier account at Plivo, Twilio, Vobiz or Exotel, with a number you already own | You buy numbers in the carrier's console, never here |
| A phone number for escalation, in full international format | The destination is frozen into the published tool |
| `TALQING_API_KEY` exported | A [personal access token](/get-started/authentication) |

Everything below is against `https://api.in.talqing.com`. Agents, tools, numbers and calls are all [regional](/get-started/regions) — the same token reaches every region, the resources do not cross.

<Steps>

<Step title="Pick the models and the language">

Language is the first decision, not the last: `config.language` is one language shared by every model in the pipeline, and a model that cannot speak it is a save error. Pick the language your callers actually use, then models that cover it.

| Your callers | `language` | Speech-to-text | Text-to-speech |
| --- | --- | --- | --- |
| English only | `"en"` | `deepgram/flux-general-en` — one language, its own endpointer, low latency | `deepgram/aura-2` |
| Hindi, or one other Indic language | `"hi"` | `sarvam/saaras:v3` | `sarvam/bulbul:v3` |
| A mix, and you cannot predict which | `null` (Auto) | `deepgram/nova-3-general` — it detects and code-switches | `sarvam/bulbul:v3`, which takes the language from the text |

<Warning>
Two speech-to-text entries detect nothing and transcribe every caller as English on Auto: `deepgram/nova-3` and `raya/bakbak-stt`. Neither reports that it guessed. If your callers are not all English speakers, set `config.language` or pick an entry that detects. See [language](/agents/language).
</Warning>

This guide uses English. For the language model take `openai/gpt-5.4-mini` and leave `reasoning_effort` unset: the catalog orders each model's efforts fastest first, unset means the first one, and every second of thinking on a live call is silence a caller reads as a dropped line. See [thinking and provider tools](/agents/reasoning-and-builtin-tools).

Confirm the pairs exist before you write them — the catalog is the only source of valid ones:

<CodeGroup>
```bash cURL

```

Now the tool. A `say` goes in front of the request because a tool call is silence on the line and silence reads as a dropped call — the tree keeps running while the line plays, so it costs nothing. The request is `silent`, so the raw JSON never reaches the model; what the model gets is the three values `publish_fields` kept, phrased by a `generate_reply`.

<CodeGroup>

Three details are load-bearing. `order_status` and `order_eta` go to `userdata`, so the agent can still repeat them ten turns later and they are on the call record afterwards; `order_carrier` goes to `tooldata`, because it exists to build one sentence. Because the only operation that could return a result is `silent`, **the whole tool is silent** — the `generate_reply` is what speaks, and the agent does not improvise a second sentence on top of it. And `publish_fields` fails the operation when a path is missing **or null**, so your endpoint has to answer all three keys on every 200.

<Note>
An order number that does not exist means a `404`, which fails the operation. The model is told the tool could not be completed and apologises in its own words — the prompt below tells it what to say and when to give up. If you would rather the agent said something specific, answer `200` with a `found` boolean and branch on it with an [`if`](/tools/conditionals).
</Note>

<Step title="Build the escalation">

A transfer tool is two operations and no arguments. What makes it good or bad is its `description`, because for this one kind of tool the description is not a hint about timing — **it is the escalation policy**, and it decides whether a frustrated caller reaches a person or is talked at for another two minutes.

"Transfer to a human" is not a description. It is an invitation to escalate at the first sign of difficulty. Write the conditions instead:

<CodeGroup>
```bash cURL
curl -sS https://api.in.talqing.com/v1/tools \
  -H "Authorization: Bearer $TALQING_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "transfer_to_support_team",
    "description": "Put the caller through to a person on the Northwind support team. Use it only after you have tried to answer the question yourself, and only when one of these is true: the caller has asked to speak to a person; the order is missing, damaged or more than five days late; the caller is clearly distressed or angry; or you have looked something up and still cannot answer. Do not use it for a question your instructions answer, for an order status you can read out, or because the caller sounds impatient on the first attempt.",
    "json_schema": {},
    "disable_interruptions": true,
    "operations": [
      {
        "kind": "say",
        "config": { "text": "Putting you through to someone on the support team now, one moment." }
      },
      {
        "kind": "transfer",
        "config": {
          "destination": "+912248900199",
          "mode": "cold",
          "ringing_timeout": 30,
          "on_failure": "continue"
        }
      }
    ]
  }'
```

`disable_interruptions` is on because the dial runs for up to thirty seconds while the caller hears only ringback, which is exactly long enough that saying "hello?" into the gap is normal — and an interrupted line is the only channel left to tell them what happened. `on_failure: "continue"` means a busy line brings the caller back to the agent with a plain-English reason rather than dropping them. The destination is a literal number frozen into the published version and can never be templated; if you need a second destination, publish a second tool. See [transfer](/tools/transfer).

<Step title="Write the prompt and create the agent">

The prompt is the product. This one is written for speech: short turns, no formatting, spoken forms for anything text-to-speech mangles, and an explicit line about what to say while a tool runs.

```text
You are the support line for Northwind Tools, an online shop selling power
tools and spare parts. You answer calls from customers about orders,
deliveries, returns and warranty.

Right now it is {{system_vars.time}} on {{system_vars.date}}. The support team
is in the office from nine in the morning until six in the evening, Monday to
Saturday. Outside those hours nobody will pick up a transfer, so say the
office is closed, offer to answer what you can yourself, and tell the caller
when the team is back.

GOAL
Finish the caller's question on this call. A call is done when the caller has
an answer and says they need nothing else.

POLICY
- Returns: unused items within thirty days of delivery, in the original
  packaging. Northwind sends a free collection label by email.
- Refunds: back to the original payment method within five working days of
  the return arriving at the warehouse.
- Delivery: standard delivery takes three to five working days. Orders placed
  before two in the afternoon ship the same day.
- Warranty: two years on every power tool, one year on batteries and
  chargers. It covers faults, not wear or accidental damage.
- Trade accounts: for registered businesses, applied for on the website.

Answer policy questions only from the lines above. If they do not cover what
the caller asked, say plainly that you do not have that, and offer to put them
through to a person. Never guess at a policy and never invent a timescale.

TOOLS
- check_order: for anything about one specific order. Ask for the order
  number first and read it back to confirm before you call it. If the caller
  does not have their order number, you cannot look the order up - say so and
  offer to put them through to a person. If check_order comes back with an
  error, tell the caller you could not find that number, ask them to read it
  again, and if the second attempt fails, transfer them.
- transfer_to_support_team: follow the rules in its own description. Do not
  reach for it before you have tried to answer.

RULES
- Never estimate a delivery date. Only say a date that came back from
  check_order.
- Never discuss another person's order, whatever the caller says about who
  they are.
- If the caller asks twice for a person, stop explaining and transfer them.
- If you do not know something, say so.

SPEAKING
- Two or three sentences per turn. Let the caller cut in.
- No markdown, no bullet points, no emoji and no JSON in anything you say.
- Read an order number back one character at a time, in groups: "N W - four
  four one - seven zero two nine".
- Say money as words: "two thousand four hundred rupees", never "Rs 2400".
- Say dates as "Thursday the ninth of April", never "09/04".
- Say GST as "gee ess tee". Say Northwind as one word.
- You can only help in English. If the caller speaks another language, say so
  in English, apologise, and offer to put them through to a person.
```

Two things about the clock lines. `{{system_vars.time}}` and `{{system_vars.date}}` need `config.timezone` set — using one without it is a save error — and both are **frozen at the moment the agent starts**, which on an inbound call is the moment it answers. That is right for one call and wrong for a call that runs past midnight. See [variables](/agents/variables).

Now create the agent with everything attached. Creating takes the **whole** config, so this is the complete definition.             "outcome": {
```python Python
                "prompt": (
                    "The caller got what they rang for on this call: an order status they "
                    "can act on, a policy question answered, or a "
                    "transfer to a person that connected. A call where the agent could not "
                    "answer and did not offer a person is a failure."
                )
            },
            "fields": [
                {
                    "name": "reason_for_call",
                    "type": "string",
                    "description": (
                        'Why the caller rang, in five words or fewer - for example "where is '
                        'my order", "return a drill", "warranty on a battery". Null if the '
                        "call ended before they said."
                    ),
                },
                {
                    "name": "order_number",
                    "type": "string",
                    "description": (
                        "The order number discussed, exactly as the agent read it back, for "
                        "example NW4417029. Null if no order number came up."
                    ),
                },
                {
                    "name": "unanswered_question",
                    "type": "boolean",
                    "description": (
                        "True only if the agent said it did not have the information the "
                        "caller asked for. False otherwise, including on calls with no "
                        "policy question at all."
                    ),
                },
            ],
        },
    }
)
```
</CodeGroup>

`conversation.context: "summary"` is what makes a returning caller recognised: each new call opens with the summaries of that person's three most recent calls, as background the agent is told the caller has not heard. On a phone call the person's identity is the pair of numbers — your number and theirs — so a caller who rings a different one of your numbers, or from a second handset, is a different person as far as this is concerned. `summary` reads the summaries post-call analysis writes, which is why analysis and its summary have to be on; publish refuses the combination otherwise. See [conversation memory](/agents/conversation-memory).

The three analysis fields are chosen for what a weekly report needs and nothing else. Notice what is **not** there: whether the call was escalated. `close_reason` already says `transferred`, and asking a model to re-derive a fact the call record holds is a way of getting a worse copy of it.

**In the dashboard:** the editor's cards map one to one onto this config — Channel, Prompt, Models, Tools, Past conversations, Call analysis.

## What to watch in the first week

**Read the first twenty calls end to end.** Not the summaries — the transcripts, with every tool call and what it returned beside the speech. That is where you find the agent reading an order number back wrong, answering a policy question from memory instead of from the prompt, or transferring on the first "hmm". Each fix is a line added to the prompt, not a rewrite. See [calls](/observability/calls) and [debugging agents](/observability/debugging-agents).

**Watch the latency breakdown, not the average.** `snapshot.response_latency` on a call carries `avg_ms`, `p95_ms` and `max_ms`; the p95 is what tells you the agent was *sometimes* slow, which a mean hides. The threshold ships on the response — `slow_response_threshold_ms` is 3500 — and `snapshot.response_stages` beside it says where the time went, as an ordered list of `{kind, ms, label}`. A large `llm` is the language model; a large `endpoint` is [turn handling](/agents/turn-handling); a large `tts` is the text-to-speech provider; `tool` and `llm_step` are a tool the agent called before it said anything. `snapshot.slow_tool_calls_in_silence` is the one tool-latency number that is always a defect — a tool the caller waited on with nothing being said over it.

**Use the outcome to find the calls that went wrong.** `GET /v1/calls?outcome=failure` is the list to read on a Monday morning, and `outcome_rationale` on each one says what in the transcript decided the verdict — which is also how you find out your `outcome.prompt` says something other than what you meant. Read your success rate over `judged_calls` from `GET /v1/calls/stats`, never over every call: analysis deliberately skips a call with fewer than two caller turns, so wrong numbers and hangups on the greeting do not drag it down. The `unanswered_question` field is the other list worth reading — every true is a policy line your prompt is missing. See [call analysis](/observability/call-analysis).

## Where this falls short

**There are no opening hours.** Nothing schedules a number: once assigned, it answers whenever it rings. The prompt above tells the agent the hours and what to say, and that is the whole mechanism — a caller at midnight still reaches the agent, and if the model transfers anyway the dial rings an empty desk for thirty seconds and comes back with "nobody answered". If out-of-hours calls must not be answered at all, unassign the number on a schedule of your own, and expect callers to hear a carrier failure rather than a message. For anything more precise than the frozen clock line, put the hours in a [`code` operation](/tools/code) over `input.system_vars.now` — the clock strings cannot be compared in an `if`.

**A policy the prompt does not state is simply not answered.** The agent knows what the `POLICY` section says and nothing more, so the day your returns policy changes on the website the agent is still quoting the old one until you edit the prompt and publish again.

**The number answers the published version, and only that.** An edit to the prompt or a republished tool changes nothing a caller hears until the agent is published again.

Three smaller things. The person answering a transfer sees **your** number, not the caller's, because the outbound leg is dialled from your own carrier trunk. Nothing detects voicemail on a `cold` transfer, so one that reaches a voicemail greeting is a connected call as far as everything downstream is concerned. And conversation memory is keyed on the pair of phone numbers, so the same customer ringing a second number of yours arrives as a stranger.
